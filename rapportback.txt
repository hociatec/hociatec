L’UI dépend fortement de l’Infrastructure partagée
Une grande partie des classes UI importe :
PHP
Copier
App\Shared\Infrastructure\Http\ApiResponse
Ce cas particulier est compréhensible, car une réponse HTTP est technique. Mais les dépendances UI → Infrastructure sont nombreuses, parfois vers des repositories ou composants concrets.
Cela révèle une architecture hybride :
• 
certains modules respectent les ports ;
• 
d’autres consomment directement Doctrine ou l’infrastructure ;
• 
certaines projections applicatives sont statiques ;
• 
certaines classes UI connaissent directement les détails techniques.
L’architecture n’est donc pas homogène. Ce n’est pas nécessairement grave pour une PME, mais en entreprise cela devient difficile à gouverner lorsque plusieurs équipes interviennent.
Séparation des responsabilités
Bonne au niveau des dossiers
Le découpage :
• 
DTO
• 
Handler
• 
Workflow
• 
Provider
• 
Writer
• 
Projection
• 
Mapper
• 
Repository
est généralement pertinent.
Moins bonne au niveau des flux
Plusieurs classes combinent encore :
• 
orchestration métier ;
• 
persistence ;
• 
gestion des transactions ;
• 
cache ;
• 
fichiers ;
• 
envoi de mail ;
• 
transformation de données ;
• 
gestion d’erreurs techniques.
Par exemple ProductWriteHandler est à la fois :
• 
validateur orchestral ;
• 
créateur d’entité ;
• 
coordinateur de galerie ;
• 
coordinateur de variantes ;
• 
coordinateur de persistence ;
• 
responsable d’invalidation du cache ;
• 
traducteur d’exception.
Le nombre de classes spécialisées autour de lui ne suffit donc pas complètement à garantir le principe de responsabilité unique.
Entités du domaine
Les entités sont relativement grandes :
• 
OrderCheckoutSession : environ 450 lignes ;
• 
TradeInRequest : environ 375 lignes ;
• 
User : environ 350 lignes ;
• 
Product : environ 350 lignes.
La taille seule n’est pas un défaut. Une entité riche peut être grande.
Dans OrderCheckoutSession, l’utilisation d’objets embarqués comme :
PHP
Copier
CheckoutPaymentState
CheckoutPricingSnapshot
CheckoutLifecycleState
est une bonne approche. Elle évite de concentrer toutes les données dans une classe plate.
Cependant, beaucoup de méthodes restent des wrappers de type getter/setter :
PHP
Copier
public function setStripePaymentStatus(...): self
{
    $this->payment->changeStripePaymentStatus(...);

    return $this;
}
Le modèle de domaine gagnerait à exposer davantage d’intentions :
PHP
Copier
$checkout->markPaymentSucceeded(...);
$checkout->markExpired();
$checkout->recordStripeFailure(...);
plutôt que des modifications indépendantes pouvant produire des états incohérents.
Les statuts sous forme de chaînes :
PHP
Copier
public const STATUS_OPEN = 'open';
public const STATUS_PAID = 'paid';
devraient progressivement devenir des enums PHP :
PHP
Copier
enum CheckoutStatus: string
{
    case Open = 'open';
    case Paid = 'paid';
    case Expired = 'expired';
    case Failed = 'failed';
}
Performance
Les points positifs :
• 
présence de pagination sur plusieurs requêtes ;
• 
utilisation de setMaxResults() et setFirstResult() ;
• 
requêtes dédiées pour le comptage ;
• 
sélection explicite de relations sur certains écrans ;
• 
mécanismes de cache pour le catalogue.
Les risques principaux :
Chargements complets
listForAdmin() sans pagination est le cas le plus évident.
Il faut rechercher et éliminer tous les :
PHP
Copier
findAll()
listAll()
resolveRecipients()
utilisés sur des ensembles dont la taille peut croître.
Hydratation d’entités pour de la lecture
Plusieurs endpoints semblent formatter des entités Doctrine :
PHP
Copier
CatalogFormatter::formatProduct($product, true)
Pour des listes, il est souvent plus performant de retourner des projections SQL/DQL en tableaux ou DTO en lecture seule, plutôt que d’hydrater tout le graphe d’entités.
Calcul des facettes
collectPublishedFacets() exécute plusieurs requêtes à partir d’un query builder cloné :
PHP
Copier
'brands' => ...
'categories' => ...
'storageCapacities' => ...
'memoryRams' => ...
'colors' => ...
'price' => ...
Cela signifie potentiellement six requêtes pour chaque chargement de catalogue, en plus de la liste et du total.
Ce choix peut rester acceptable avec :
• 
les bons index ;
• 
un cache efficace ;
• 
une faible fréquence d’invalidation ;
• 
un volume raisonnable.
Mais il faut le mesurer. Le catalogCache->clear() global après chaque écriture risque également d’invalider beaucoup plus de données que nécessaire.
Appels externes dans les requêtes HTTP
Les e-mails, PDF, sauvegardes, chiffrement et appels Stripe doivent être vérifiés pour s’assurer que les traitements longs sont asynchrones lorsqu’ils n’ont pas besoin d’être synchrones.
Maintenabilité
Les facteurs favorables :
• 
noms de classes explicites ;
• 
arborescence prévisible ;
• 
beaucoup de petites classes ;
• 
typage strict ;
• 
peu de code de débogage abandonné ;
• 
peu de contrôleurs géants ;
• 
exceptions métier dédiées.
Les facteurs défavorables :
• 
signatures positionnelles très longues ;
• 
duplication de délégation ;
• 
couches parfois artificielles ;
• 
dépendances Application → Infrastructure ;
• 
incohérence dans l’utilisation des ports ;
• 
multiples styles de persistence ;
• 
nombreux commit() dispersés ;
• 
tableaux array<string, mixed> ;
• 
paramètres métier représentés par de simples chaînes ;
• 
formatters statiques ;
• 
logique de requête répétée dans les contrôleurs.
