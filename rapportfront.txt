AUDIT COMPLET DU FRONTEND
Frontend React / TypeScript connecté à une API PHP
===================================================

CONTEXTE
--------

L’archive analysée contient environ :
- 585 fichiers ;
- 44 000 lignes TypeScript/TSX ;
- 7 500 lignes CSS.

Le frontend possède un bon socle, mais il est désormais assez volumineux pour nécessiter des règles d’architecture beaucoup plus strictes. Les principaux risques sont la dispersion des responsabilités, la duplication, le manque de tests et plusieurs fragilités autour de l’authentification, du CSRF et des contrats avec l’API PHP.

Limite de l’analyse :
L’archive contient surtout le dossier src. Sans package.json, tsconfig, configuration Vite, ESLint, CI et lockfile, il n’est pas possible de confirmer que le projet compile ni d’auditer précisément les dépendances.


10. ACCESSIBILITÉ
=================

10.1 Auditer tous les dialogues
-------------------------------

Les composants de dialogue doivent gérer :
- role="dialog" ou alertdialog ;
- aria-modal ;
- titre accessible ;
- description ;
- piégeage du focus ;
- fermeture par Échap ;
- retour du focus ;
- blocage du scroll ;
- ordre de tabulation.


10.2 Vérifier les boutons à icône
---------------------------------

Tout bouton sans texte visible doit avoir :

    aria-label="Supprimer le produit"

Le title seul ne suffit pas.


10.3 Ne pas utiliser la couleur seule
-------------------------------------

Les statuts doivent posséder :
- texte ;
- icône éventuellement ;
- couleur.

Exemple : « Paiement échoué » et pas uniquement une pastille rouge.


10.4 Contrôler les annonces aria-live
-------------------------------------

Le composant AccessibilityAnnouncer est un bon signal.

Il faut éviter :
- annonces répétitives ;
- annonces trop longues ;
- relecture complète de la page ;
- annonces lors de simples mouvements visuels.


10.6 Vérifier le contraste
--------------------------

Particulièrement pour :
- textes gris ;
- placeholders ;
- badges ;
- états désactivés ;
- erreurs ;
- boutons secondaires ;
- liens visités.


10.7 Ajouter des tests automatisés Axe
--------------------------------------

À intégrer dans les tests de composants ou Playwright.

Les tests automatisés ne remplacent pas un audit clavier manuel, mais détectent beaucoup d’erreurs simples.


11. PERFORMANCE
===============

11.4 Virtualiser les grandes listes
-----------------------------------

Pour :
- produits ;
- clients ;
- commandes ;
- tickets ;
- audits ;
- historiques.

Utiliser pagination serveur ou virtualisation.

Ne jamais charger des milliers d’éléments dans le DOM.


11.5 Déplacer les filtres lourds côté serveur
---------------------------------------------

Le frontend ne doit pas télécharger toutes les données pour filtrer localement.

Le backend doit supporter :
- pagination ;
- tri ;
- recherche ;
- filtres ;
- champs sélectionnés.


11.6 Optimiser les images
-------------------------

Pour le catalogue :
- WebP ou AVIF ;
- dimensions fixes ;
- srcset ;
- lazy loading ;
- placeholder ;
- compression ;
- CDN si nécessaire.

Exemple :

    <img
      loading="lazy"
      decoding="async"
      width={400}
      height={300}
    />


11.7 Éviter les re-rendus massifs des contextes
-----------------------------------------------

AuthContext, CartContext, Toast et autres providers entourent toute l’application.

Vérifier que chaque changement ne rerend pas inutilement un grand arbre.

Solutions :
- séparer état et actions ;
- découper les contextes ;
- utiliser des sélecteurs ;
- mémoriser correctement les valeurs ;
- placer les providers au niveau nécessaire.


11.8 Éviter le polling lorsque non nécessaire
---------------------------------------------

Plusieurs hooks utilisent setInterval :
- audits admin ;
- détail d’audit ;
- audits client ;
- liste d’audits.

Il faut vérifier :
- nettoyage de l’intervalle ;
- arrêt lorsque l’onglet est masqué ;
- arrêt une fois l’opération terminée ;
- absence de polling simultané ;
- backoff en cas d’erreur ;
- intervalle raisonnable.

React Query peut gérer cela avec refetchInterval.


11.9 Éviter les requêtes en cascade
-----------------------------------

Une page ne devrait pas faire :
1. requête utilisateur ;
2. puis requête catégorie ;
3. puis requête produits ;
4. puis requête détails de chaque produit.

Le backend peut fournir un endpoint adapté ou le frontend peut paralléliser les appels indépendants.

12.2 Tester le client HTTP en profondeur
----------------------------------------

Cas obligatoires :
- ajout du token panier ;
- ajout CSRF uniquement pour méthodes sensibles ;
- exclusion CSRF pour l’endpoint de token ;
- 401 puis refresh réussi ;
- plusieurs 401 simultanés ;
- un seul refresh réel ;
- refresh échoué ;
- pas de boucle infinie ;
- requête de refresh elle-même en 401 ;
- renouvellement CSRF ;
- réponse métier en HTTP 200 ;
- upload FormData ;
- timeout ;
- annulation.


12.3 Tester l’authentification
------------------------------

Parcours :
- session existante ;
- session absente ;
- session expirée ;
- panne réseau ;
- login réussi ;

- logout backend réussi ;
- logout backend échoué ;
- suppression de compte ;

Chaque route d’administration doit avoir des tests pour :
- utilisateur anonyme ;
- client ;

12.5 Tester les formulaires

- upload invalide ;

12.6 Ajouter MSW
----------------

Mock Service Worker permet de simuler l’API PHP à un niveau proche du réseau réel.

Cela évite de mocker directement toutes les fonctions API et permet de tester :
- headers ;
- cookies simulés ;
- statuts ;
- latence ;
- erreurs ;
- réponses incorrectes.

12.8 Ajouter des tests visuels
------------------------------

Utile pour :

15. SEO ET MÉTADONNÉES
======================

15.1 Centraliser les métadonnées
--------------------------------

useMetaTags.ts est utile, mais il faut vérifier :
- titre unique ;
- canonical correct ;
- description ;
- Open Graph ;
- Twitter Cards ;
- robots ;
- URL absolue ;
- image sociale.


15.2 Ne pas indexer les pages privées
-------------------------------------

Ajouter noindex aux pages :
- compte ;
- commandes ;
- devis ;
- admin ;
- connexion ;
- panier ;
- paiement ;
- bêta.

Le serveur doit également empêcher l’indexation lorsque pertinent.


15.3 Vérifier le rendu des pages publiques

Pour un catalogue public important, envisager :
- SSR ;
- pré-rendu ;
- génération statique ;
- sitemap produit ;
- données structurées JSON-LD.


16. EXPÉRIENCE UTILISATEUR
==========================

16.1 Uniformiser tous les états de page
---------------------------------------

Chaque page chargée depuis l’API doit posséder :
- skeleton ou chargement ;
- erreur ;
- état vide ;
- contenu ;
- permission refusée ;
- ressource introuvable.

Créer des composants communs :

    PageLoading
    PageError
    EmptyState
    ForbiddenState
    NotFoundState


16.2 Distinguer erreur vide et vraie absence de données
-------------------------------------------------------

Ne jamais afficher « Aucun élément » après une requête qui a échoué.

Un tableau vide et une erreur réseau sont deux situations différentes.


16.3 Ajouter des confirmations adaptées
---------------------------------------

Une confirmation ne doit pas être systématique pour chaque action.

Elle est nécessaire pour :
- suppression ;
- remboursement ;
- annulation irréversible ;
- envoi marketing ;
- changement critique de statut ;
- restauration de sauvegarde.

Pour les actions réversibles, préférer parfois « Annuler » dans un toast.


16.4 Empêcher les actions incompatibles
---------------------------------------

Les boutons doivent dépendre du véritable état métier.

Exemple : ne pas afficher « Payer » si la commande est :
- annulée ;
- remboursée ;
- expirée ;
- déjà payée ;
- bloquée.

Le backend doit naturellement refaire ce contrôle.


16.5 Afficher des dates et heures explicites
--------------------------------------------

Pour les rendez-vous et opérations :

    5 août 2026 à 14:30, heure de Paris

et pas seulement :

    05/08 14:30

Ajouter le fuseau lorsque cela peut être ambigu.


16.6 Prévoir les connexions lentes
----------------------------------

Afficher une progression et ne pas laisser un bouton paraître bloqué.

Pour les opérations longues :
- message de traitement ;
- polling contrôlé ;
- possibilité de quitter la page ;
- notification lorsque terminé si le système le permet.


17. ADMINISTRATION
==================

17.1 Ajouter une traçabilité des actions
----------------------------------------

Toute action administrateur sensible doit produire un audit backend :
- qui ;
- quoi ;
- quand ;
- ancienne valeur ;
- nouvelle valeur ;
- adresse IP ou contexte pertinent ;
- requestId.

Le frontend peut afficher cet historique, mais ne doit pas en être la source.


17.2 Séparer lecture et modification
------------------------------------

Les pages de détail administratives ne doivent pas mettre toutes les données directement en édition.

Préférer :
- mode lecture ;
- bouton Modifier ;
- validation ;
- annulation ;
- indication de sauvegarde.


17.3 Gérer les modifications concurrentes
-----------------------------------------

Deux administrateurs peuvent modifier la même ressource.

Utiliser :
- un champ version ;
- updatedAt ;
- ETag / If-Match ;
- ou un mécanisme de verrouillage optimiste.

En cas de conflit, retourner 409 Conflict.


17.4 Paginer les historiques
----------------------------

Les audits, commentaires, commandes et événements ne doivent pas être chargés intégralement.

Pagination curseur recommandée pour les historiques.


17.5 Encadrer les exports
-------------------------

Pour CSV, PDF et sauvegardes :
- permissions strictes ;
- expiration des URLs ;
- protection contre l’injection CSV ;
- limites de volume ;
- suivi des exports ;
- traitement asynchrone côté serveur si lourd.

Les valeurs CSV commençant par =, +, - ou @ doivent être neutralisées.

CONCLUSION
----------

Le projet est déjà sérieux et bien plus structuré qu’un frontend improvisé. Son principal problème est désormais son échelle : il a grandi plus vite que ses garanties automatiques.

Pour atteindre un niveau réellement robuste en production, la priorité doit aller :
- à la sécurité des flux ;
- au contrat API ;
- aux tests ;
- à la réduction des responsabilités dispersées ;
- à l’unification des composants et conventions ;
- à l’observabilité ;
- à l’automatisation des contrôles de qualité.
