AUDIT COMPLET DU FRONTEND
Frontend React / TypeScript connecté à une API PHP
===================================================

CONTEXTE
--------

L’archive analysée contient environ :
- 585 fichiers ;
- 44 000 lignes TypeScript/TSX ;
- 7 500 lignes CSS.

Le frontend possède un bon socle, mais il est désormais assez volumineux pour nécessiter des règles d’architecture beaucoup plus strictes. Les principaux risques sont la dispersion des responsabilités, la duplication, le manque de tests et plusieurs fragilités autour de l’authentification, du CSRF et des contrats avec l’API PHP.

Limite de l’analyse :
L’archive contient surtout le dossier src. Sans package.json, tsconfig, configuration Vite, ESLint, CI et lockfile, il n’est pas possible de confirmer que le projet compile ni d’auditer précisément les dépendances.


16. EXPÉRIENCE UTILISATEUR
==========================

16.1 Uniformiser tous les états de page
---------------------------------------

Chaque page chargée depuis l’API doit posséder :
- skeleton ou chargement ;
- erreur ;
- état vide ;
- contenu ;
- permission refusée ;
- ressource introuvable.

Créer des composants communs :

    PageLoading
    PageError
    EmptyState
    ForbiddenState
    NotFoundState


16.2 Distinguer erreur vide et vraie absence de données
-------------------------------------------------------

Ne jamais afficher « Aucun élément » après une requête qui a échoué.

Un tableau vide et une erreur réseau sont deux situations différentes.


16.3 Ajouter des confirmations adaptées
---------------------------------------

Une confirmation ne doit pas être systématique pour chaque action.

Elle est nécessaire pour :
- suppression ;
- remboursement ;
- annulation irréversible ;
- envoi marketing ;
- changement critique de statut ;
- restauration de sauvegarde.

Pour les actions réversibles, préférer parfois « Annuler » dans un toast.


16.4 Empêcher les actions incompatibles
---------------------------------------

Les boutons doivent dépendre du véritable état métier.

Exemple : ne pas afficher « Payer » si la commande est :
- annulée ;
- remboursée ;
- expirée ;
- déjà payée ;
- bloquée.

Le backend doit naturellement refaire ce contrôle.


16.5 Afficher des dates et heures explicites
--------------------------------------------

Pour les rendez-vous et opérations :

    5 août 2026 à 14:30, heure de Paris

et pas seulement :

    05/08 14:30

Ajouter le fuseau lorsque cela peut être ambigu.


16.6 Prévoir les connexions lentes
----------------------------------

Afficher une progression et ne pas laisser un bouton paraître bloqué.

Pour les opérations longues :
- message de traitement ;
- polling contrôlé ;
- possibilité de quitter la page ;
- notification lorsque terminé si le système le permet.


17. ADMINISTRATION
==================

17.1 Ajouter une traçabilité des actions
----------------------------------------

Toute action administrateur sensible doit produire un audit backend :
- qui ;
- quoi ;
- quand ;
- ancienne valeur ;
- nouvelle valeur ;
- adresse IP ou contexte pertinent ;
- requestId.

Le frontend peut afficher cet historique, mais ne doit pas en être la source.


17.2 Séparer lecture et modification
------------------------------------

Les pages de détail administratives ne doivent pas mettre toutes les données directement en édition.

Préférer :
- mode lecture ;
- bouton Modifier ;
- validation ;
- annulation ;
- indication de sauvegarde.


17.3 Gérer les modifications concurrentes
-----------------------------------------

Deux administrateurs peuvent modifier la même ressource.

Utiliser :
- un champ version ;
- updatedAt ;
- ETag / If-Match ;
- ou un mécanisme de verrouillage optimiste.

En cas de conflit, retourner 409 Conflict.


17.4 Paginer les historiques
----------------------------

Les audits, commentaires, commandes et événements ne doivent pas être chargés intégralement.

Pagination curseur recommandée pour les historiques.


17.5 Encadrer les exports
-------------------------

Pour CSV, PDF et sauvegardes :
- permissions strictes ;
- expiration des URLs ;
- protection contre l’injection CSV ;
- limites de volume ;
- suivi des exports ;
- traitement asynchrone côté serveur si lourd.

Les valeurs CSV commençant par =, +, - ou @ doivent être neutralisées.


18. MAINTENABILITÉ
==================

18.1 Ajouter une documentation d’architecture
---------------------------------------------

Créer un document expliquant :
- structure des features ;
- règles d’import ;
- client HTTP ;
- gestion des erreurs ;
- authentification ;
- React Query ;
- design system ;
- tests ;
- conventions API.


18.2 Ajouter une checklist de revue de code
-------------------------------------------

Exemples :
- permissions vérifiées côté backend ;
- aucune donnée sensible dans le stockage ;
- erreur gérée ;
- loading et état vide ;
- tests ajoutés ;
- accessibilité ;
- pas de requête en boucle ;
- invalidation du cache ;
- responsive ;
- traduction et formatage.


18.3 Ajouter des limites automatiques
-------------------------------------

Des règles peuvent signaler :
- fichiers trop longs ;
- fonctions trop complexes ;
- trop de branches ;
- trop de paramètres ;
- imports interdits ;
- dépendances circulaires.

Ne pas imposer aveuglément une limite, mais utiliser les alertes pour guider les refactorisations.


18.4 Supprimer le code mort
---------------------------

Avec 585 fichiers, mettre en place :
- détection des exports inutilisés ;
- détection des dépendances inutilisées ;
- détection du CSS inutilisé ;
- suppression des anciennes variantes de composants.

Outils possibles :
- knip ;
- depcheck ;
- analyse de couverture ;
- rapport CSS.


18.5 Standardiser les noms
--------------------------

Choisir une convention stable :
- *Api.ts pour les appels ;
- use*Query.ts ;
- use*Mutation.ts ;
- *Page.tsx ;
- *Dialog.tsx ;
- *.types.ts ;
- *.schema.ts ;
- *.mapper.ts.

Éviter le mélange entre api.ts, cartApi.ts, operationsApiShared.ts, etc., sans règle explicite.

CONCLUSION
----------

Le projet est déjà sérieux et bien plus structuré qu’un frontend improvisé. Son principal problème est désormais son échelle : il a grandi plus vite que ses garanties automatiques.

Pour atteindre un niveau réellement robuste en production, la priorité doit aller :
- à la sécurité des flux ;
- au contrat API ;
- aux tests ;
- à la réduction des responsabilités dispersées ;
- à l’unification des composants et conventions ;
- à l’observabilité ;
- à l’automatisation des contrôles de qualité.
