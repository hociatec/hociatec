AUDIT COMPLET DU FRONTEND
Frontend React / TypeScript connecté à une API PHP
===================================================

CONTEXTE
--------

L’archive analysée contient environ :
- 585 fichiers ;
- 44 000 lignes TypeScript/TSX ;
- 7 500 lignes CSS.

Le frontend possède un bon socle, mais il est désormais assez volumineux pour nécessiter des règles d’architecture beaucoup plus strictes. Les principaux risques sont la dispersion des responsabilités, la duplication, le manque de tests et plusieurs fragilités autour de l’authentification, du CSRF et des contrats avec l’API PHP.

Limite de l’analyse :
L’archive contient surtout le dossier src. Sans package.json, tsconfig, configuration Vite, ESLint, CI et lockfile, il n’est pas possible de confirmer que le projet compile ni d’auditer précisément les dépendances.


1. SÉCURITÉ CRITIQUE
=====================

1.7 Ne pas faire confiance aux types TypeScript pour les données API
--------------------------------------------------------------------

TypeScript vérifie le code à la compilation, pas les données reçues du PHP.

Cette écriture :

    const response = await httpClient.get<Order>('/orders/123');

ne garantit pas que le serveur renvoie réellement un Order.

Correction recommandée :

    const OrderSchema = z.object({
      id: z.string(),
      status: z.enum(['pending', 'paid', 'cancelled']),
      total: z.number().nonnegative(),
    });

    const order = OrderSchema.parse(response.data);

À appliquer au minimum sur :
- utilisateur connecté ;
- commandes ;
- paiements ;
- devis ;
- droits ;
- produits administrables ;
- URLs de paiement ;
- imports et exports.


1.8 Vérifier le stockage du token panier
----------------------------------------

Le frontend utilise un X-Cart-Token persistant.

Ce token ne doit jamais :
- donner accès aux données personnelles du client ;
- permettre de lire un panier uniquement par connaissance de l’identifiant ;
- être prédictible ;
- rester valable indéfiniment ;
- devenir un substitut à une session authentifiée.

Le backend doit générer un token aléatoire suffisamment long, le faire expirer et éventuellement le hacher en base.

3. CLIENT HTTP ET CONTRAT API
=============================

3.1 Unifier le format des réponses PHP
--------------------------------------

Le frontend semble accepter plusieurs formes :
- succès HTTP classique ;
- erreur HTTP ;
- erreur métier dans une réponse HTTP 200 ;
- réponses enveloppées ;
- réponses directement typées.

Le fait que l’intercepteur appelle createApiResponseError(response.data) sur toutes les réponses indique qu’une réponse 200 peut contenir une erreur métier.

Cela rend le protocole ambigu.

Format recommandé pour un succès :

    {
      "data": {},
      "meta": {},
      "message": null
    }

Format recommandé pour une erreur :

    {
      "error": {
        "code": "ORDER_NOT_PAYABLE",
        "message": "Cette commande ne peut plus être payée.",
        "fields": {},
        "requestId": "req_123"
      }
    }

Avec des statuts HTTP corrects :
- 400 requête invalide ;
- 401 non authentifié ;
- 403 interdit ;
- 404 introuvable ;
- 409 conflit ;
- 422 validation ;
- 429 limite ;
- 500 serveur.


3.8 Générer le client depuis OpenAPI
------------------------------------

Le nombre important de modules API augmente le risque de divergence.

Mettre en place :
1. une spécification OpenAPI côté PHP ;
2. la génération des types TypeScript ;
3. éventuellement la génération des méthodes clientes ;
4. une validation CI du contrat.

Cela évite les différences de :
- noms de champs ;
- valeurs d’énumération ;
- nullabilité ;
- pagination ;
- formats de date ;
- statuts d’erreur.


4. REACT QUERY ET GESTION DES DONNÉES
=====================================

4.1 React Query est encore sous-utilisé
---------------------------------------

Le projet contient :
- environ 716 occurrences de useState ;
- environ 260 occurrences de useEffect.

React Query est bien utilisé dans les fonctionnalités bêta, mais beaucoup d’autres domaines semblent conserver une gestion manuelle des chargements.

Cela entraîne souvent :
- duplication des états loading/error/data ;
- absence de cache ;
- requêtes concurrentes ;
- données périmées ;
- invalidations oubliées ;
- code plus difficile à tester.

Correction :

Utiliser React Query pour toutes les données serveur :
- commandes ;
- devis ;
- produits ;
- catégories ;
- rendez-vous ;
- favoris ;
- formations ;
- profil ;
- audits ;
- listes administratives.


4.6 Utiliser les mutations plutôt que des états manuels
-------------------------------------------------------

Les actions comme :
- annulation ;
- suppression ;
- validation ;
- création ;
- modification ;

doivent utiliser useMutation.

Cela centralise :
- isPending ;
- erreurs ;
- invalidations ;
- notifications ;
- désactivation des boutons.


5. ARCHITECTURE DU PROJET
=========================

5.1 Définir des frontières de modules
-------------------------------------

L’organisation par features est bonne, mais elle doit être renforcée par des règles.

Architecture recommandée :

    app/
    features/
    shared/

Règles :
- shared ne dépend jamais de features ;
- une feature n’importe pas les internals d’une autre feature ;
- les dépendances inter-features passent par un publicApi.ts ;
- app compose les features ;
- les pages ne sont pas importées par les composants.

Ajouter des règles ESLint avec no-restricted-imports ou un outil comme Dependency Cruiser.


5.2 Généraliser les publicApi.ts
--------------------------------

Le catalogue possède déjà un publicApi.ts, mais cette convention ne semble pas généralisée.

Chaque domaine devrait exposer uniquement ce qui est public :

    export { ProductsPage } from './pages/ProductsPage';
    export { useProduct } from './hooks/useProduct';
    export type { Product } from './types';

Interdire les imports profonds inter-domaines.


5.4 Réduire les fichiers fourre-tout
------------------------------------

Plusieurs fichiers sont importants en taille :
- AdminTradeInDetailsSections.tsx
- AdminBetaTestersPage.tsx
- AdminBugReportDetailDialog.tsx
- ProductsListPage.tsx
- AdminDashboardOperationalSections.tsx
- RegisterFormFields.tsx
- useAdminTradeInsPage.ts
- useAdminBugReportsController.ts
- useAdminBetaCampaignsController.ts

Un gros fichier n’est pas automatiquement mauvais, mais ces fichiers semblent susceptibles de cumuler :
- récupération des données ;
- transformation ;
- état local ;
- validation ;
- rendu ;
- dialogues ;
- actions ;
- permissions.

Correction recommandée :

    AdminTradeInDetails/
      AdminTradeInHeader.tsx
      AdminTradeInCustomerSection.tsx
      AdminTradeInDeviceSection.tsx
      AdminTradeInValuationSection.tsx
      AdminTradeInHistory.tsx
      useAdminTradeInDetails.ts
      adminTradeInMappers.ts


5.5 Éviter les hooks contrôleurs trop massifs
---------------------------------------------

Les hooks comme useAdmin...Controller sont utiles, mais peuvent devenir des composants invisibles contenant toute l’application.

Découper entre :
- requêtes ;
- mutations ;
- état de filtres ;
- dialogues ;
- sélection ;
- formulaires ;
- logique métier.

Exemple :

    useBugReportQueries
    useBugReportMutations
    useBugReportFilters
    useBugReportSelection


5.6 Ne pas réexporter toute une feature sans contrôle
-----------------------------------------------------

features/catalog/publicApi.ts fait partie des fichiers importants en taille. Un fichier public trop volumineux peut :
- masquer les dépendances ;
- créer des cycles ;
- charger involontairement beaucoup de code ;
- rendre les imports imprécis.

Créer plusieurs points d’entrée si nécessaire :

    features/catalog/public
    features/catalog/admin
    features/catalog/types


5.8 Réduire les imports globaux de CSS
--------------------------------------

Si les styles de toutes les fonctionnalités sont chargés depuis main.tsx ou un fichier global, l’utilisateur télécharge du CSS inutile.

Charger le CSS au niveau de la route ou du composant lorsque cela est possible.


6. QUALITÉ TYPESCRIPT
=====================

6.1 Bon point : aucune occurrence évidente de any
-------------------------------------------------

L’analyse ne montre pas d’usage explicite notable de any. C’est positif.

Il faut toutefois vérifier le tsconfig, absent de l’archive.

Activer idéalement :

    {
      "strict": true,
      "noUncheckedIndexedAccess": true,
      "exactOptionalPropertyTypes": true,
      "noImplicitOverride": true,
      "noFallthroughCasesInSwitch": true,
      "useUnknownInCatchVariables": true
    }


6.3 Utiliser des unions discriminées
------------------------------------

Pour les états complexes :

    type LoadState<T> =
      | { status: 'idle' }
      | { status: 'loading' }
      | { status: 'success'; data: T }
      | { status: 'error'; error: AppError };

C’est plus sûr que plusieurs booléens pouvant devenir incohérents.


6.4 Ne pas dupliquer les enums frontend/backend
-----------------------------------------------

Les statuts de :
- commandes ;
- devis ;
- audits ;
- remboursements ;
- campagnes ;
- tickets ;

doivent provenir d’une source contractuelle commune.

Sinon, le PHP peut ajouter un statut que le frontend ne reconnaît pas.


6.5 Utiliser des types opaques pour les identifiants
----------------------------------------------------

Tous les identifiants en string sont interchangeables par erreur.

Créer des types :

    type OrderId = string & { readonly __brand: 'OrderId' };
    type ProductId = string & { readonly __brand: 'ProductId' };

Ce n’est pas obligatoire partout, mais utile dans les domaines sensibles.


6.6 Séparer DTO et modèles d’affichage
--------------------------------------

Le type renvoyé par l’API ne doit pas forcément être le type utilisé dans le composant.

Créer :
- OrderDto ;
- Order ;
- OrderViewModel.

Une fonction de mapping permet de normaliser les dates, montants et valeurs optionnelles.


7. GESTION DES ERREURS
======================

7.3 Centraliser les notifications
---------------------------------

De nombreux composants semblent décider eux-mêmes quand afficher un toast.

Créer des conventions :
- succès de mutation : toast bref ;
- validation : erreur près du champ ;
- erreur globale : bannière ;
- erreur de chargement : état de page ;
- suppression : confirmation et toast ;
- erreur silencieuse : uniquement si réellement non importante.


7.5 Fournir une action Réessayer
--------------------------------

Les états d’erreur réseau doivent afficher une action explicite :

    <Button onClick={() => refetch()}>
      Réessayer
    </Button>

Pas seulement un message statique.


8. FORMULAIRES ET VALIDATION
============================

8.1 Uniformiser la bibliothèque de formulaires
----------------------------------------------

Le grand nombre de pages et de formulaires suggère une gestion possiblement hétérogène.

Standardiser autour de :
- React Hook Form ;
- Zod ;
- composants de champs communs ;
- mapping des erreurs 422.


8.2 Afficher les erreurs serveur au niveau des champs
-----------------------------------------------------

Le PHP devrait renvoyer :

    {
      "error": {
        "code": "VALIDATION_ERROR",
        "fields": {
          "email": ["Cette adresse est déjà utilisée."],
          "password": ["Le mot de passe est trop court."]
        }
      }
    }

Le frontend doit relier ces erreurs aux champs correspondants.


8.3 Ne pas dupliquer les règles métier uniquement côté frontend
---------------------------------------------------------------

La validation frontend améliore l’UX, mais le PHP doit refaire toutes les vérifications.

Exemples :
- quantité disponible ;
- montant ;
- réduction ;
- statut de commande ;
- format de fichier ;
- droits ;
- créneau disponible ;
- date limite ;
- prix actuel.


8.4 Désactiver correctement les doubles soumissions
---------------------------------------------------

Tous les boutons de formulaire doivent utiliser l’état réel de mutation :

    disabled={mutation.isPending}

Mais il faut aussi une idempotence backend, car la désactivation visuelle ne suffit pas.


8.5 Gérer le focus sur la première erreur
-----------------------------------------

Après validation :
- focus sur le premier champ invalide ;
- message global pour lecteurs d’écran ;
- aria-describedby ;
- aria-invalid.


8.6 Ne pas effacer les formulaires après une erreur
---------------------------------------------------

Conserver les données déjà saisies, sauf champs sensibles comme les mots de passe lorsque nécessaire.


8.7 Protéger les modifications non sauvegardées
------------------------------------------------

Sur les formulaires administratifs longs :
- avertissement lors de la navigation ;
- distinction entre état initial et état modifié ;
- sauvegarde automatique éventuelle ;
- brouillons côté serveur si nécessaire.

16. EXPÉRIENCE UTILISATEUR
==========================

16.1 Uniformiser tous les états de page
---------------------------------------

Chaque page chargée depuis l’API doit posséder :
- skeleton ou chargement ;
- erreur ;
- état vide ;
- contenu ;
- permission refusée ;
- ressource introuvable.

Créer des composants communs :

    PageLoading
    PageError
    EmptyState
    ForbiddenState
    NotFoundState


16.2 Distinguer erreur vide et vraie absence de données
-------------------------------------------------------

Ne jamais afficher « Aucun élément » après une requête qui a échoué.

Un tableau vide et une erreur réseau sont deux situations différentes.


16.3 Ajouter des confirmations adaptées
---------------------------------------

Une confirmation ne doit pas être systématique pour chaque action.

Elle est nécessaire pour :
- suppression ;
- remboursement ;
- annulation irréversible ;
- envoi marketing ;
- changement critique de statut ;
- restauration de sauvegarde.

Pour les actions réversibles, préférer parfois « Annuler » dans un toast.


16.4 Empêcher les actions incompatibles
---------------------------------------

Les boutons doivent dépendre du véritable état métier.

Exemple : ne pas afficher « Payer » si la commande est :
- annulée ;
- remboursée ;
- expirée ;
- déjà payée ;
- bloquée.

Le backend doit naturellement refaire ce contrôle.


16.5 Afficher des dates et heures explicites
--------------------------------------------

Pour les rendez-vous et opérations :

    5 août 2026 à 14:30, heure de Paris

et pas seulement :

    05/08 14:30

Ajouter le fuseau lorsque cela peut être ambigu.


16.6 Prévoir les connexions lentes
----------------------------------

Afficher une progression et ne pas laisser un bouton paraître bloqué.

Pour les opérations longues :
- message de traitement ;
- polling contrôlé ;
- possibilité de quitter la page ;
- notification lorsque terminé si le système le permet.

Préférer :

- bouton Modifier ;
- validation ;
- annulation ;
- indication de sauvegarde.


17.3 Gérer les modifications concurrentes
-----------------------------------------

Deux administrateurs peuvent modifier la même ressource.

Utiliser :
- un champ version ;
- updatedAt ;
- ETag / If-Match ;
- ou un mécanisme de verrouillage optimiste.

En cas de conflit, retourner 409 Conflict.


17.4 Paginer les historiques
----------------------------

Les audits, commentaires, commandes et événements ne doivent pas être chargés intégralement.

Pagination curseur recommandée pour les historiques.


17.5 Encadrer les exports
-------------------------

Pour CSV, PDF et sauvegardes :
- permissions strictes ;
- expiration des URLs ;
- protection contre l’injection CSV ;
- limites de volume ;
- suivi des exports ;
- traitement asynchrone côté serveur si lourd.

Les valeurs CSV commençant par =, +, - ou @ doivent être neutralisées.
