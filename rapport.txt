Évaluation des 17 points
6. Persistance et repositories — 8/10
Les repositories sont correctement situés dans Infrastructure.
La séparation avec les transactions et l’unité de travail est plus claire.
Le repository du catalogue a été fortement réduit par rapport aux premières versions.
Limite importante
J’ai trouvé environ 47 classes Application dépendant directement d’une classe Infrastructure du même module.
Par exemple, un service applicatif peut importer directement :
PHP
Copier
use App\Module\User\Infrastructure\Repository\UserRepository;
Cela fonctionne, mais viole l’inversion de dépendance d’une architecture hexagonale stricte.
La direction idéale est :
Copier
Application
→ interface de repository
← implémentation Doctrine dans Infrastructure
Par exemple :
Copier
User/Application/Port/UserRepository.php
User/Infrastructure/Repository/DoctrineUserRepository.php
Il ne faut pas forcément le faire pour chaque petite requête, mais pour les agrégats principaux :
• 
User ;
• 
Order ;
• 
Product ;
• 
Quote ;
• 
TradeIn ;
• 
Voucher.
 
7. Autorisations — 9/10
Les anciennes vérifications manuelles ont disparu.
Les quelques occurrences de getRoles() restantes correspondent principalement :
• 
à l’exposition du profil ;
• 
à la méthode de l’entité User ;
• 
à un formatter.
Ce ne sont pas des contrôles d’autorisation dispersés.
Les policies dédiées constituent une bonne protection contre les IDOR.
Pour atteindre 10
Ajouter systématiquement des tests comme :
Copier
User A ne peut pas consulter la commande de User B
User A ne peut pas télécharger la facture de User B
User A ne peut pas commenter le rapport de User B
Un admin peut accéder selon une règle explicitement documentée
Et séparer clairement :
• 
droits techniques liés aux rôles ;
• 
règles métier liées à l’état de la ressource.

9. Fichiers et documents — 8,5/10
Les générateurs PDF sont maintenant sous :
Copier
Order/Infrastructure/Pdf/
Quote/Infrastructure/Pdf/
C’est le bon emplacement.
Les réponses de fichiers sont centralisées avec AttachmentResponseFactory.
Reste à améliorer
Les classes PDF restent très longues :
Copier
QuotePdfService            317 lignes
OrderInvoicePdfService     314 lignes
Elles peuvent probablement être divisées en :
Copier
QuotePdfDataBuilder
QuotePdfTemplateRenderer
QuotePdfGenerator
QuotePdfFilenameFactory
Même logique pour les factures.
Il faut aussi confirmer hors de src :
• 
antivirus ;
• 
limites globales d’upload ;
• 
stockage hors web root ;
• 
configuration du serveur web ;
• 
rétention et suppression.
 
10. Outbox et appels externes — 9,5/10
C’est maintenant l’une des parties les plus solides.
Tu as ajouté ou confirmé :
• 
FOR UPDATE SKIP LOCKED ;
• 
réservation concurrente sûre ;
• 
récupération des événements bloqués en processing ;
• 
catch (\Throwable) ;
• 
statut dead ;
• 
métriques ;
• 
alertes ;
• 
purge des événements finalisés ;
• 
âge du plus ancien événement ;
• 
corrélation avec request_id.
C’est une vraie implémentation de production, pas une simple table d’événements.
Pourquoi pas 10 ?
Il faudrait valider avec des tests d’intégration réels :
• 
deux workers concurrents ;
• 
crash après réservation ;
• 
crash après effet externe mais avant marquage comme traité ;
• 
événement sans handler ;
• 
événement non récupérable ;
• 
dépassement du nombre maximal de tentatives ;
• 
reprise d’un événement stale ;
• 
purge.
L’outbox garantit l’« au moins une fois », donc les handlers externes doivent eux-mêmes être idempotents.
 
11. DTO et validation — 8,5/10
Tu as environ 79 objets dans les catégories :
Copier
DTO
Input
Command
Query
La situation est beaucoup meilleure que dans la première version où plusieurs services recevaient directement des tableaux JSON.
Reste à uniformiser
Le projet semble encore utiliser plusieurs conventions :
Copier
DTO/
Dto/
Input/
Command/
Query/
Il faut définir clairement :
Copier
Input     = représentation HTTP validée
Command   = intention d’écriture applicative
Query     = intention de lecture
DTO       = transfert interne exceptionnel
Et éviter qu’un Input Symfony contenant des contraintes de validation traverse tout le domaine.
 
12. Réponses API et mapping — 8/10
Des projections et formatters spécialisés ont été introduits :
Copier
Application/Projection/
Application/Operations/Projection/
C’est une amélioration.
Cependant, certains formatters restent très gros, par exemple :
Copier
AdminOperationsFormatter : environ 208 lignes
Et certains objets de présentation sont encore dans Application alors qu’ils semblent produire directement un format HTTP.
Recommandation
Séparer :
Copier
Application/Projection
pour les modèles de lecture indépendants du transport ;
et :
Copier
UI/Http/Response
UI/Http/Mapper
pour le JSON final.
 
13. Repositories et requêtes — 8,5/10
Le découpage des lectures a beaucoup progressé.

Reste à surveiller
UserRepository fait encore environ 265 lignes et OrderRepository environ 203 lignes.
Ce n’est pas excessif en soi, mais il faut vérifier qu’ils ne mélangent pas :
• 
chargement d’agrégat ;
• 
recherche admin ;
• 
recherche publique ;
• 
statistiques ;
• 
exports ;
• 
pagination complexe.
La règle recommandée :
Copier
Repository d’agrégat
≠
Query service
≠
Projection de tableau de bord

16. Cohérence de conception — 8/10
La cohérence a beaucoup progressé :
• 
Handler pour certains cas d’utilisation ;
• 
Projection pour les lectures ;
• 
Policy pour les droits ;
• 
Infrastructure/Pdf pour les PDF ;
• 
Shared/Domain pour les value objects ;
• 
transaction abstraite correctement placée.
Mais le projet conserve plusieurs styles concurrents :
Copier
Service
Handler
Manager
Provider
Writer
Updater
Projection
Formatter
Workflow
Cette diversité est acceptable seulement si chaque suffixe possède une définition officielle.
Convention recommandée
Suffixe
Rôle
Handler
exécute un cas d’utilisation
Provider
fournit une donnée ou une lecture
Projection
construit un modèle de lecture
Calculator
calcul pur
Policy
prend une décision
Workflow
orchestre des transitions
Mapper
transforme un format vers un autre
Gateway 
port vers un système externe
Repository
charge et sauvegarde un agrégat
Service 
réservé aux rares comportements ne correspondant à aucun rôle plus précis
Copier le tableau
