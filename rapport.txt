Évaluation des 17 points
11. DTO et validation — 8,5/10
Tu as environ 79 objets dans les catégories :
Copier
DTO
Input
Command
Query
La situation est beaucoup meilleure que dans la première version où plusieurs services recevaient directement des tableaux JSON.
Reste à uniformiser
Le projet semble encore utiliser plusieurs conventions :
Copier
DTO/
Dto/
Input/
Command/
Query/
Il faut définir clairement :
Copier
Input     = représentation HTTP validée
Command   = intention d’écriture applicative
Query     = intention de lecture
DTO       = transfert interne exceptionnel
Et éviter qu’un Input Symfony contenant des contraintes de validation traverse tout le domaine.
 
12. Réponses API et mapping — 8/10
Des projections et formatters spécialisés ont été introduits :
Copier
Application/Projection/
Application/Operations/Projection/
C’est une amélioration.
Cependant, certains formatters restent très gros, par exemple :
Copier
AdminOperationsFormatter : environ 208 lignes
Et certains objets de présentation sont encore dans Application alors qu’ils semblent produire directement un format HTTP.
Recommandation
Séparer :
Copier
Application/Projection
pour les modèles de lecture indépendants du transport ;
et :
Copier
UI/Http/Response
UI/Http/Mapper
pour le JSON final.
 
13. Repositories et requêtes — 8,5/10
Le découpage des lectures a beaucoup progressé.
Les providers et projections limitent le besoin d’utiliser un repository unique pour toutes les recherches.
Reste à surveiller
UserRepository fait encore environ 265 lignes et OrderRepository environ 203 lignes.
Ce n’est pas excessif en soi, mais il faut vérifier qu’ils ne mélangent pas :
• 
chargement d’agrégat ;
• 
recherche admin ;
• 
recherche publique ;
• 
statistiques ;
• 
exports ;
• 
pagination complexe.
La règle recommandée :
Copier
Repository d’agrégat
≠
Query service
≠
Projection de tableau de bord

L’outbox possède maintenant :
• 
métriques ;
• 
alertes ;

•

• 
request ID ;

logs.

Copier
Prometheus
Grafana
Sentry
Datadog
OpenTelemetry
ELK
Et confirmer :
• 
taux d’erreur par route ;
• 
latence ;
• 
métriques Stripe ;
• 
âge des événements outbox ;
• 
échec d’emails ;
• 
échec de sauvegardes ;
• 
journal d’audit administrateur ;
• 
alertes exploitables.
 
16. Cohérence de conception — 8/10
La cohérence a beaucoup progressé :
• 
Handler pour certains cas d’utilisation ;
• 
Projection pour les lectures ;
• 
Policy pour les droits ;
• 
Infrastructure/Pdf pour les PDF ;
• 
Shared/Domain pour les value objects ;
• 
transaction abstraite correctement placée.
Mais le projet conserve plusieurs styles concurrents :
Copier
Service
Handler
Manager
Provider
Writer
Updater
Projection
Formatter
Workflow
Cette diversité est acceptable seulement si chaque suffixe possède une définition officielle.
Convention recommandée
Suffixe
Rôle
Handler
exécute un cas d’utilisation
Provider
fournit une donnée ou une lecture
Projection
construit un modèle de lecture
Calculator
calcul pur
Policy
prend une décision
Workflow
orchestre des transitions
Mapper
transforme un format vers un autre
Gateway 
port vers un système externe
Repository
charge et sauvegarde un agrégat
Service 
réservé aux rares comportements ne correspondant à aucun rôle plus précis
Copier le tableau
