2. Responsabilités des contrôleurs
État : 🟢 très bien corrigé

Ils sont également correctement déplacés dans :
Copier
UI/Controller/
C’est exactement leur place.
Tu as conservé environ 234 contrôleurs, ce qui n’est pas un problème puisque beaucoup sont orientés action.
Reste à surveiller
Un contrôleur doit uniquement :
• 
recevoir et convertir l’entrée HTTP ;
• 
appeler un cas d’utilisation ;
• 
produire la réponse HTTP.
Il ne doit pas devenir un simple ancien contrôleur déplacé sous UI.

7. Autorisations
État : 🟢 très bien corrigé
Les vérifications manuelles de rôles sont passées à zéro.
Les policies sont désormais dans les domaines :
Copier
Order/Domain/Security/
Quote/Domain/Security/
TradeIn/Domain/Security/
Appointment/Domain/Security/
La centralisation des droits réduit fortement les risques d’IDOR.
Nuance
Une policy d’autorisation qui dépend du système de rôles Symfony ne devrait pas être trop profondément intégrée au domaine.
Il faut distinguer :
• 
règle métier : « le propriétaire peut annuler une commande non expédiée » ;
• 
règle de sécurité applicative : « un administrateur peut accéder à cette route ».
Les voters Symfony ou policies applicatives peuvent gérer la seconde.

10. Outbox, emails et appels externes
État : 🟢 grande amélioration
L’outbox est maintenant beaucoup plus robuste.
Les problèmes précédemment signalés ont été corrigés :
• 
réservation transactionnelle ;
• 
verrouillage via findDueForUpdate() ;
• 
catch (\Throwable) ;
• 
événement sans handler marqué dead ;
• 
compteur uniquement incrémenté lorsque le traitement est effectif ;
• 
métriques ajoutées ;
• 
request ID associé.
Le dispatcher est devenu nettement plus fiable.
Points encore à vérifier
La robustesse réelle dépend de l’implémentation de :
PHP
Copier
findDueForUpdate()
Il faut vérifier qu’elle utilise vraiment :
• 
un verrou pessimiste ;
• 
idéalement SKIP LOCKED ;
• 
une transaction couvrant la réservation.
Il faut aussi gérer les événements restés en processing après un crash du worker.
Exemple :
Copier
processing depuis plus de 15 minutes
→ remettre en pending ou failed
Le token de reset reste stocké en clair dans le payload outbox. Une purge rapide ou un chiffrement du payload serait préférable.
