
======================================================================
1. OBJECTIF DU RAPPORT
======================================================================

Le backend possède déjà une architecture modulaire sérieuse, une séparation globale
entre Domain, Application, Infrastructure et UI, ainsi qu’un vocabulaire métier
riche. La note actuelle peut être estimée autour de 7,5/10 sur le plan purement
architectural.

Pour dépasser 9/10, il ne faut pas réécrire le projet. Il faut consolider les
frontières existantes, réduire les classes centrales trop volumineuses et rendre
les règles métier plus explicites.

Une note supérieure à 9/10 suppose que les critères suivants soient atteints :

- responsabilités des classes clairement identifiables ;
- dépendances entre couches strictement maîtrisées ;
- modules métier réellement autonomes ;
- agrégats de taille raisonnable ;
- règles métier indépendantes des détails HTTP et techniques ;
- états impossibles difficilement représentables ;
- orchestration applicative lisible ;
- génération documentaire structurée ;
- conventions homogènes dans l’ensemble du projet ;
- absence de nouvelles classes monolithiques.

======================================================================
2. PRIORITÉS ABSOLUES
======================================================================

Les actions suivantes sont indispensables. Tant qu’elles ne sont pas réalisées,
une note supérieure à 9/10 ne serait pas crédible.

----------------------------------------------------------------------
2.1 RETIRER HTTPFOUNDATION DE LA COUCHE APPLICATION
----------------------------------------------------------------------

Constat :
Plusieurs classes de la couche Application manipulent directement Request,
UploadedFile, Cookie ou d’autres objets propres à Symfony HttpFoundation.

Problème :
La couche Application connaît le canal HTTP et les conventions du framework.
Elle ne peut donc pas être considérée comme totalement indépendante de l’interface.

Actions :

[ ] Déplacer tous les mappers recevant Symfony\Component\HttpFoundation\Request
    vers la couche UI.

[ ] Déplacer les traitements liés aux champs multipart, fichiers envoyés,
    paramètres de requête, query strings et cookies vers UI/Http ou UI/Mapper.

[ ] Faire produire par la couche UI des objets applicatifs explicites :
    - Command ;
    - Input ;
    - Criteria ;
    - WriteData ;
    - UploadData ;
    - DTO d’entrée.

[ ] Interdire les imports suivants dans Application :
    - Symfony\Component\HttpFoundation\Request ;
    - Symfony\Component\HttpFoundation\Response ;
    - Symfony\Component\HttpFoundation\JsonResponse ;
    - Symfony\Component\HttpFoundation\UploadedFile ;
    - Symfony\Component\HttpFoundation\Cookie.

[ ] Remplacer les ports exposant directement des concepts HTTP par des ports
    exprimant une intention métier ou applicative.

Exemple de structure cible :

UI/Http/Mapper/ProductRequestMapper
    -> ProductWriteData
Application/Catalog/ProductWriteHandler
    -> manipule uniquement ProductWriteData

Critère de validation :
Aucun fichier situé dans */Application/* ne doit importer HttpFoundation, sauf
exception explicitement documentée et justifiée.

Impact attendu :
Très élevé. Cette correction renforce immédiatement la cohérence des couches.

2.2 RÉDUIRE LES AGRÉGATS SURDIMENSIONNÉS

- TradeInRequest ;

Constat :

Actions générales :

[ ] Lister les responsabilités de chaque grosse entité.

[ ] Identifier les groupes de données qui évoluent ensemble.

[ ] Extraire les concepts cohérents sous forme de value objects ou d’objets
    embarqués.

[ ] Réduire les constructeurs à un état initial minimal et valide.

[ ] Déplacer les données apparaissant uniquement dans une phase ultérieure vers
    des méthodes métier dédiées.

[ ] Supprimer les setters génériques lorsque la modification correspond à une

[ ] Exprimer les opérations sous forme de verbes métier.

Exemples :

- submit();
- acceptOffer();
- refuseOffer();
- registerPayment();
- attachDocument();
- close();
- cancel();
- expire();
- applyDiscount();
- changeCondition();

Critère de validation :
Une entité principale ne doit pas obliger l’appelant à connaître toutes les
phases futures de son cycle de vie lors de sa création.

----------------------------------------------------------------------

Objets possibles :

- TradeInApplicant ;
- TradeInProductSnapshot ;
- TradeInEstimate ;
- TradeInConsent ;
- TradeInOffer ;
- TradeInPaymentDetails ;
- TradeInClosure ;

[ ] Conserver dans l’état initial uniquement les informations nécessaires à la

[ ] Ajouter les informations de paiement uniquement au moment de la validation
    du paiement.

[ ] Ajouter les documents uniquement au moment de leur réception.

[ ] Ajouter les informations de clôture uniquement lors de la clôture.

[ ] Remplacer les champs de statut représentés par des chaînes par des enums.

À préférer :

Critère de validation :
Il doit être impossible de créer ou modifier une demande de reprise dans un état
financièrement ou fonctionnellement incohérent.

2.5 RÉDUIRE LE NOMBRE DE DÉPENDANCES PAR CLASSE
----------------------------------------------------------------------

Constat :
Certaines classes possèdent 9 à 12 dépendances injectées.

Actions :

[ ] Examiner toute classe ayant plus de 7 dépendances.

[ ] Déterminer si elle orchestre plusieurs cas d’usage.

[ ] Découper les phases indépendantes.

[ ] Introduire des services de haut niveau lorsque plusieurs dépendances forment
    une collaboration cohérente.

[ ] Ne jamais créer un ServiceBag ou un objet contenant artificiellement toutes
    les dépendances.

[ ] Ne jamais injecter le conteneur de services.

Seuils recommandés :

- 1 à 5 dépendances : normal ;
- 6 à 7 : à surveiller ;
- 8 et plus : revue de responsabilité obligatoire.

Critère de validation :
Les classes ayant plus de 7 dépendances doivent être exceptionnelles et
documentées.

----------------------------------------------------------------------
3.4 SUPPRIMER LES NORMALISATIONS SILENCIEUSES DANGEREUSES
----------------------------------------------------------------------

Actions :

[ ] Rechercher les usages de :
    - max(0, ...) ;
    - min(...) correctif ;
    - abs(...) sur des données métier ;
    - trim suivi d’une acceptation sans validation ;
    - valeur par défaut masquant une entrée invalide ;
    - catch d’exception vide ;
    - conversion silencieuse d’un état inconnu.

[ ] Classer chaque cas :
    - normalisation légitime ;
    - correction silencieuse dangereuse.

[ ] Lever des exceptions métier explicites pour les incohérences.

[ ] Faire remonter les erreurs de données à la frontière appropriée.

Critère de validation :
Une anomalie financière, d’état ou d’identité ne doit jamais être transformée
silencieusement en donnée valide.

----------------------------------------------------------------------
3.5 RENFORCER LES INVARIANTS
----------------------------------------------------------------------

Pour chaque agrégat principal :

[ ] Documenter les invariants.

[ ] Vérifier les invariants à la construction.

[ ] Vérifier les invariants lors de chaque transition.

[ ] Empêcher les modifications directes contournant les règles.

Exemples d’invariants :

- total de commande non négatif ;
- quantité strictement positive ;
- montant remboursé inférieur ou égal au montant payé ;
- estimation maximale supérieure ou égale à l’estimation minimale ;
- voucher non utilisé après expiration ;
- commande payée non repassable en attente sans opération explicite ;
- demande clôturée non modifiable ;
- devise identique entre lignes et total ;
- remise inférieure au montant éligible.

Critère de validation :
Les règles critiques doivent être garanties par le modèle, et non dépendre de la
discipline des appelants.

Critère de validation :
Une règle de commande ne doit pas avoir deux implémentations, une côté client et

9. CONVENTIONS DE NOMMAGE
======================================================================

----------------------------------------------------------------------
9.1 NORMALISER LES SUFFIXES
----------------------------------------------------------------------

Convention recommandée :

- Handler : point d’entrée d’un cas d’usage ;
- Workflow : processus métier en plusieurs étapes ;
- Policy : décision ou éligibilité ;
- Calculator : calcul pur ;
- Factory : construction complexe ;
- Mapper : transformation structurelle ;
- Converter : conversion entre modèles métier ;
- Normalizer : nettoyage ou canonicalisation ;
- Provider : lecture ou composition de données ;
- Projection : modèle de lecture ;
- Formatter : représentation finale ;
- Port : contrat avec l’extérieur ;
- Repository : persistance d’un agrégat ;
- Renderer : production d’un format ;
- Scheduler : planification d’une action ;
- Notifier : notification métier.

Actions :

[ ] Recenser les classes nommées Service.

[ ] Renommer celles dont la responsabilité est plus précise.

[ ] Conserver Service uniquement lorsqu’aucun terme métier plus exact ne convient.

[ ] Éliminer les noms vagues :
    - Manager ;
    - Helper ;
    - Utils ;
    - CommonService ;
    - DataService ;
    - OperationsService, lorsque plusieurs opérations sans cohérence y sont
      regroupées.

Critère de validation :
Le nom d’une classe doit permettre de prévoir son rôle principal.

----------------------------------------------------------------------
9.2 UNIFORMISER COMMAND, INPUT ET DATA
----------------------------------------------------------------------

Actions :

[ ] Définir une convention :
    - Command pour un ordre de mutation ;
    - Query pour une demande de lecture ;
    - Input pour des données de cas d’usage ;
    - WriteData pour des données de modification structurées ;
    - Criteria pour des filtres ;
    - Projection pour une sortie de lecture.

[ ] Éviter plusieurs suffixes différents pour des rôles identiques.

Critère de validation :
Deux classes jouant le même rôle doivent utiliser le même vocabulaire.

- classe supérieure à 7 dépendances : revue obligatoire.

Actions :

[ ] Examiner chaque dépassement.

[ ] Extraire uniquement des responsabilités nommables.

[ ] Ne pas découper artificiellement une méthode en petites méthodes sans sens.

[ ] Préférer des méthodes privées exprimant le scénario métier.

[ ] Éviter les niveaux d’imbrication profonds.

[ ] Utiliser les retours anticipés pour les cas d’erreur.

Critère de validation :
La lecture du code doit suivre le flux métier sans naviguer dans une multitude de
détails secondaires.

----------------------------------------------------------------------
11.2 SUPPRIMER LES BOOLÉENS AMBIGUS
----------------------------------------------------------------------

Actions :

[ ] Rechercher les méthodes avec plusieurs paramètres booléens.

[ ] Remplacer les booléens représentant des modes par :
    - enum ;
    - option nommée ;
    - méthode spécialisée ;
    - objet de configuration métier.

Mauvais :

process($order, true, false, true)

Meilleur :

process($order, ProcessingMode::ADMINISTRATIVE_OVERRIDE)

Critère de validation :
Aucun appel ne doit nécessiter de connaître la signification de plusieurs true
ou false positionnels.

12. SÉCURITÉ DE CONCEPTION
======================================================================

Sans traiter l’infrastructure de sécurité ou l’outillage, les règles suivantes
concernent directement le code.

Actions :

[ ] Ne jamais placer de secret dans les classes.

[ ] Ne jamais enregistrer de données bancaires ou privées dans des logs métier.

[ ] Séparer les documents privés des documents publics.

[ ] Encapsuler les accès aux ressources sensibles derrière des ports.

[ ] Vérifier les autorisations au niveau du cas d’usage, pas uniquement dans le
    contrôleur, lorsque l’opération peut être invoquée par plusieurs canaux.

[ ] Éviter les identifiants prédictibles pour les ressources publiques.

[ ] Prévoir l’anonymisation et la suppression logique lorsque le domaine conserve

Critère de validation :
Un autre canal d’entrée ne doit pas pouvoir contourner une règle d’autorisation
présente uniquement dans l’interface HTTP.

- Ajouter une interface à chaque classe.
- Créer une factory pour chaque objet.

- Découper toutes les méthodes uniquement pour réduire leur nombre de lignes.
- Créer une couche Shared contenant toutes les abstractions.
- Réécrire l’application depuis zéro.
- Appliquer un modèle DDD théorique sans bénéfice métier concret.

L’objectif est une architecture claire et pragmatique, pas une accumulation de
patterns.

======================================================================
19. RISQUES PENDANT LA REMÉDIATION
======================================================================

Risque 1 : surarchitecture

Prévention :
N’extraire une classe que lorsqu’une responsabilité cohérente peut être nommée.

Risque 2 : déplacement sans amélioration

Prévention :
Déplacer HttpFoundation vers UI, mais ne pas recréer un mapper géant ailleurs.

Risque 3 : services intermédiaires artificiels

Prévention :
Ne pas créer des façades dont le seul rôle est de cacher dix dépendances.

Risque 4 : value objects excessifs

Prévention :
Prioriser les valeurs possédant de vraies règles.

Risque 5 : duplication pendant la transition

Prévention :
Migrer un workflow complet avant de conserver deux chemins parallèles.

Risque 6 : fragmentation excessive

Prévention :
Une classe de cinq lignes n’est pas automatiquement meilleure qu’une classe de
cinquante lignes cohérentes.

Risque 7 : incohérence entre anciens et nouveaux modules

Prévention :
Définir les conventions avant de lancer les refactorisations massives.
